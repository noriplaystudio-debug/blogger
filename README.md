# Blogger 주간 글쓰기 에이전트

## v12 글 생성 안정화

- 선택 제목과 제목 후보가 문장부호·띄어쓰기만 다른 경우 자동으로 일치시킵니다.
- 제목 평가 설명, 메타 설명, 라벨, 답변 요약, 사실 점검표가 일부 누락되면 초안에서 안전하게 복구합니다.
- 작성·검수 모델이 JSON 대신 일반 응답을 보내면 전용 복구 요청을 한 번 수행합니다.
- 검수 형식만 끝내 복구하지 못한 경우 완성된 초안을 버리지 않고 `검토 필요`로 저장합니다.
- 공식 1차 출처가 확보된 경우 동일 공식 도메인의 URL 경로 차이 때문에 조사가 차단되지 않도록 실제 검색 URL에 다시 연결합니다.
- 인증·결제·사용량 제한처럼 반복 실행해도 해결되지 않는 오류만 즉시 중단합니다.
- 선택한 검수 모델이 형식 오류를 반복하면 연결된 OpenAI 검수 모델로 자동 전환해 다시 검수합니다.
- 자동 검수만 실패한 초안은 본문을 즉시 볼 수 있도록 자동으로 펼쳐 표시합니다.
- 근거 부족 작업은 일일 작성량에서 제외하고 같은 키워드의 다른 글 방향, 다음 우선순위 키워드 순서로 대체합니다.
- `NEEDS_REVIEW` 상태의 완성 초안도 사용자가 선택해 Blogger 임시글로 저장할 수 있습니다. 공개는 별도 승인 전까지 차단됩니다.

한국 공개 검색 관심도를 바탕으로 카테고리·키워드·글을 조사하고 작성하는 개인용 웹앱입니다. 카테고리 수, 카테고리별 키워드 수, 키워드별 글 수, 하루 작성량은 대시보드에서 언제든 바꿀 수 있습니다.

## 작업 흐름

1. OpenAI·Anthropic·Gemini API 키를 연결합니다.
2. 동일한 조건으로 세 모델의 작성 능력과 검수 능력을 따로 비교합니다.
3. 작성 모델과 검수 모델을 각각 선택합니다. 같은 모델 또는 서로 다른 모델을 사용할 수 있습니다.
4. 원하는 카테고리 수·키워드 수·키워드별 글 수·하루 작성량을 입력합니다.
5. 주간 시장 조사를 실행해 설정 수량을 상한으로 품질 기준을 통과한 작업만 대기열에 넣고, 매일 설정한 수만큼 자료 조사·작성·독립 검수·재작성을 자동 실행합니다.
6. 통과한 글은 Blogger 임시글로 자동 저장합니다.
7. 마지막 승인 버튼을 누른 글만 공개합니다.
8. Search Console 성과를 매주 분석하고, 충분한 표본에서 반복된 개선점을 다음 계획·작성·검수에 반영합니다.
9. 수익 사령탑이 실제 AdSense 수익과 페이지 RPM을 읽어 목표 격차를 계산하고 다음 주의 확대·보완·측정 지시를 주간 계획에 반영합니다.

## 장기 검색형과 실시간 관심형 배분

- 주간 계획은 `evergreen`(장기 검색형)과 `realtime`(실시간 관심형)을 별도 기준으로 평가합니다.
- 기본적으로 카테고리의 약 40%, 최소 1개를 검증 가능한 사건·연예·스포츠 등 실시간 관심 트랙으로 우선 검토합니다. 카테고리 수를 1개로 줄여도 실시간 후보를 먼저 검토합니다.
- 사건은 공공기관 발표·교통·안전·서비스 변경·후속 절차, 연예는 공식 작품·방송·공연·음악·차트·수상 정보, 스포츠는 공식 일정·결과·기록·규정·공개 발표를 다룹니다.
- 연예인 사생활·루머, 피해자 신상·잔혹 묘사, 확인되지 않은 원인·책임 단정, 정치 선동 등은 조회수가 높아도 제외합니다.
- 실시간 글은 대기열 앞쪽에서 작성하며 6·24·72·168시간 중 하나의 현재성 확인 주기를 가집니다. 유효시간이 지난 Blogger 임시글은 재조사·재작성 전까지 공개할 수 없습니다.

작성 모델 비교 결과는 HTML 코드 대신 제목·문단·목록·표가 배치된 Blogger 대표 화면으로 먼저 표시됩니다. 실제 블로그 테마에 따라 글꼴과 폭은 달라질 수 있으며, 각 샘플의 `HTML 원문 보기`에서 생성 코드를 별도로 확인할 수 있습니다. 검수 비교에서는 점수와 발견한 문제를 먼저 보여주고 수정 결과가 HTML이면 같은 방식으로 미리봅니다. 미리보기는 서버에서 허용된 HTML만 남긴 뒤 렌더링하므로 스크립트나 위험한 속성을 실행하지 않습니다.

## 편집 안전장치

- 키워드만으로 글을 만들지 않고 최신 공개자료를 먼저 조사합니다.
- 공식기관·제조사·공공자료 등 1차 출처를 우선합니다.
- 조사 결과를 독자 질문, 직접 답변, 출처가 연결된 검증 주장, 출처 간 충돌, 확인 불가 사항, 실행 단계로 구조화합니다.
- 사용하지 않은 제품, 방문하지 않은 장소, 존재하지 않는 개인 경험을 꾸며내지 않습니다.
- 근거가 없는 숫자·날짜·가격·효과를 만들지 않습니다.
- 문제해결형, 비교형, 체크리스트형, 초보자형, 오해와 사실형, 사례 분석형, FAQ형 구조를 글마다 선택합니다.
- 단순한 출처 재요약이 아니라 비교 기준, 계산, 체크리스트, 의사결정 절차, 예외 정리 중 주제에 맞는 독자 가치를 반드시 추가합니다.
- 작성 모델과 별도로 검수 모델이 사실성, 근거성, 유용성, 검색 의도, 독창 가치, 가독성, 제목 정확성, 완결성을 점수화합니다.
- 모든 점수 기준을 통과한 원고만 OpenAI 웹 검색으로 원문을 다시 여는 최종 근거 감사를 받습니다. 미확인 주장, 조건 왜곡, 오래된 정보가 하나라도 남으면 자동 통과하지 않습니다.
- 종합 88점, 사실성·근거성 95점, 유용성 88점, 검색 의도·제목 정확성·완결성 90점, 독창 가치·가독성 85점, 동일 블로그 기존 글 유사도 40% 미만을 모두 충족해야 자동 통과합니다.
- 계획 단계에서 요청량의 최소 2배 후보를 내부 조사하고, 최종 키워드마다 서로 다른 근거 도메인 2곳을 확보한 항목을 우선 선정합니다.
- 출처 조사가 막히면 독립 출처 보강과 검증 범위 축소를 최대 3단계로 시도합니다. 그래도 부족한 작업만 `source_blocked`로 격리하고 나머지 대기열은 계속 처리합니다.
- 작성·검수의 일시적인 JSON 형식 오류나 기술 검증 실패는 최대 3회까지 자동 수정합니다. 점수 기준을 끝내 통과하지 못한 완성 원고는 사람 검토 상태로 남깁니다.
- 브라우저 종료나 새로고침 중 `working`에 멈춘 로컬 작업은 다음 실행에서 재시도 가능한 상태로 자동 복구합니다.
- 독자 목적이 비슷한 카테고리 2~4개를 하나의 주제군 Blogger로 묶고, 묶음별 Blogger와 문체를 지정할 수 있습니다. 카테고리가 충분하면 3~4개 묶음을 우선합니다.
- 예약 자동공개를 켜면 매일 오전 9시(한국시간)에 최대 설정 수량(기본 7개)을 작성하고, 모든 품질·근거·현재성 기준을 통과한 글만 Blogger에 공개합니다. 일반 주제는 과거 발행 글과 중복을 차단하고, 실시간·계절·사건 날짜형 주제는 동일 사건·날짜가 아닐 때 다시 허용합니다. 개별 글 오류는 후보를 교체해 계속 시도하고 인증·쿼터·결제 같은 공통 공급자 오류만 즉시 중지합니다.
- 수익 사령탑에서 AdSense와 제휴 링크, 협찬·스폰서, 체크리스트·템플릿 같은 디지털 상품을 함께 선택할 수 있습니다. 에이전트는 제휴 가입·계약·결제를 임의로 수행하지 않으며, 관계 고지·환불·개인정보 절차와 외부 계정 연결 상태를 대시보드에서 관리합니다.
- 비용 최적화: 계획 단계에서 이미 검증한 일반형 근거 문서는 글마다 재검색하지 않고 재사용합니다. 실시간·고위험 주제는 독립 웹 감사를 유지하며, 과거 콘텐츠·성과 쿼리·수익 분석 입력은 필요한 최신 요약만 전달합니다. 저장된 계획·완료 작업은 새로 검색하지 않습니다.
- API 키는 클라이언트 저장소에 기록하지 않고 암호화된 HTTP-only 세션 쿠키에 보관합니다.

## 제목 작성 기술

Google은 제목에 고정 글자 수 제한을 제시하지 않고 설명적이고 간결하며 페이지마다 고유한 제목을 권장합니다. 이 에이전트의 **12~70자**는 검색 노출을 보장하는 공식 기준이 아니라 지나치게 짧거나 장황한 자동 생성 제목을 막기 위한 내부 운영 범위입니다.

1. 작성 모델은 같은 제목을 조금씩 고치는 대신 `직접 답변형`, `대상·조건형`, `비교 기준형`, `문제 해결형` 후보를 각각 하나씩 만듭니다.
2. 후보마다 검색 질문 적합성, 본문이 이행할 약속, 과장·모호성·현재성 위험을 기록합니다.
3. 네 후보 중 본문이 완전히 증명할 수 있고 기존 제목과 구별되는 하나를 선택하고 선택 이유를 남깁니다.
4. 검수 모델은 질문 일치, 구체성, 정확성, 차별성, 간결성을 각각 점수화하고 필요하면 제목을 다시 씁니다.
5. 코드는 제목 길이, 핵심 키워드 반복, 기존 제목 유사도 62% 미만, 느낌표·물음표와 구분자 남용, 과장·공포·상투 문구를 다시 검사합니다.
6. `총정리`, `완벽 가이드`, `한눈에 보기`, `모르면 손해` 같은 상투 표현과 확인되지 않은 연도·가격·숫자는 허용하지 않습니다.
7. 메타 설명은 제목 복사본이 아니라 대상·답변 범위·읽을 이유를 50~150자로 별도 설명합니다.

Google이 검색 결과 제목을 페이지의 `<title>`, 대표 제목, 제목 요소와 본문 등 여러 신호로 생성할 수 있으므로 제목과 실제 본문의 핵심 답이 어긋나지 않도록 검수합니다. 참고: [Google 제목 링크 권장사항](https://developers.google.com/search/docs/appearance/title-link)

## 본문 작성 기술

| 구간        | 작성 규칙                                                            | 코드·검수 기준                                                |
| ----------- | -------------------------------------------------------------------- | ------------------------------------------------------------- |
| 첫 문단     | 인사나 목차 예고 없이 질문에 직접 답하고 핵심 조건·예외를 함께 제시  | 35~320자, `answerSummary`와 의미 일치                         |
| 소제목      | 각 구획에서 얻을 답을 구체적으로 표현                                | H2/H3 2~9개, 중복 및 `서론·본론·결론·정리` 같은 빈 제목 금지  |
| 문단        | 문단 하나에 핵심 하나만 배치                                         | 최소 4문단, 500자 초과 문단은 최대 2개                        |
| 키워드      | 검색어를 자연스럽게 필요한 곳에만 사용                               | 제목 내 동일 핵심어 1회 이하, 본문 길이에 따른 반복 상한 적용 |
| 근거        | 사실 문장 가까이에 의미 있는 앵커 텍스트로 원문 연결                 | URL 자체를 링크 문구로 쓰지 않음, 검증 출처 도메인 2곳 이상   |
| 고유 가치   | 비교표·계산·체크리스트·의사결정 절차·예외 정리 중 적합한 결과물 제공 | `valueAdd` 필수, 독창 가치 점수 85점 이상                     |
| 예시        | 실제 체험으로 꾸미지 않고 가정임을 명시                              | 허위 경험 및 근거 밖 주장 검수                                |
| 마지막 구획 | 요약 반복 대신 다음 행동·적용 제외 상황·재확인 시점 제시             | 완결성 90점 이상                                              |

최종 원고에는 제목 길이, 기존 제목·본문 유사도, 문단·소제목·긴 문단·키워드·출처 링크 수를 포함한 `제목·본문 기술 진단`이 저장됩니다. 사용자가 제목이나 본문을 직접 고치면 기존 점수가 수정 전 기준임을 화면에 경고합니다. Blogger 임시저장과 최종 공개 직전에도 제목, 본문 길이, 소제목, 검증 출처 링크를 다시 검사합니다. Google의 공식 안내처럼 읽기 쉽고 잘 정리되어 있으며 고유하고 최신인 콘텐츠를 목표로 합니다. 참고: [Google SEO 기본 가이드](https://developers.google.com/search/docs/fundamentals/seo-starter-guide)

- AdSense가 승인 전이거나 계정·RPM 데이터가 없으면 `수익 검증 단계`로 표시하고 거짓 예측을 만들지 않습니다.

### 사업 손익과 예산 안전장치

- AdSense의 사이트 도메인별 최근 30일 예상 수익·페이지뷰를 Blogger별로 연결해 매출, RPM, 예상 비용, 예상 순이익을 비교합니다.
- API 비용은 OpenAI 실제 청구서를 읽은 값이 아닙니다. 사용자가 정한 글 1개 예상 비용에는 사실 조사·작성·검수·최종 웹 근거 감사를 포함해 입력해야 합니다. 주간 조사 1회, 블로그별 성과 분석 1회, 수익 전략 1회 예상 비용과 서버·도메인 등 월 고정비도 직접 입력합니다.
- 월 AI 예산을 설정하고 `예산 초과 전 조사·작성·분석 중지`를 켜면 다음 작업의 예상 비용까지 포함해 한도를 넘기기 전에 실행을 멈춥니다. 비용 확인과 예약은 하나의 DB 트랜잭션으로 처리해 실행이 겹쳐도 한도를 넘지 않도록 합니다.
- 도메인이 맞지 않아 블로그에 귀속하지 못한 AdSense 수익은 별도 금액으로 표시해 잘못된 성과 확대를 막습니다.
- 블로그별 신청 준비도는 공개 글 내부 목표, 소개·문의·개인정보처리방침 페이지, 해당 블로그의 Search Console 신호를 점검합니다. 이는 운영 체크리스트이며 AdSense 승인을 보장하지 않습니다.
- AdSense 계정 연결만으로 승인되었다고 판정하지 않습니다. Blogger 도메인과 일치하는 AdSense 사이트 상태가 `READY`일 때만 승인 완료로 표시합니다.

- 대시보드의 `예약 자동 실행`을 끄고 저장하면 주간 조사, 성과 분석, 수익 전략, 일일 작성을 모두 긴급 중지할 수 있습니다.
- 같은 예약 작업이 동시에 호출돼도 DB 잠금으로 한 번만 실행됩니다. 잠금은 실행 오류에 대비해 자동 만료됩니다.
- 자동 작성 재시도마다 예상 비용을 별도로 기록합니다. 예산이 부족해 이미 선점한 작업은 시도 횟수를 소모하지 않고 다시 대기 상태로 돌립니다.
- Blogger 임시글에는 내부 작업 표식을 넣습니다. 네트워크 오류 후 재시도해도 같은 작업의 임시글을 다시 찾아 중복 생성을 줄입니다.
- 사람이 임시저장하거나 공개한 상태는 데이터베이스에도 즉시 반영되므로 새로고침 후에도 대시보드와 성장 단계가 일치합니다.
- 같은 주에 시장 조사를 다시 실행하면 아직 시작하지 않은 기존 대기 작업만 새 계획으로 교체합니다. 작성 중·검수 완료·임시저장·공개 글은 보존하고, 동일한 주제·각도의 완료 글을 새 대기열에 중복으로 넣지 않습니다.
- 블로그 연결 전에 품질 검수를 통과한 글은 연결 후 다음 일일 실행에서 추가 AI 호출 없이 Blogger 임시글로 옮깁니다.
- 이미 만든 Blogger 임시글을 대시보드에서 수정해 다시 저장하면 기존 임시글 자체를 갱신합니다. 새 임시글을 중복 생성하거나 수정 전 내용을 공개하지 않습니다.
- Blogger에서 임시글을 직접 삭제한 뒤 대시보드에서 다시 저장하면 삭제 사실을 확인하고 같은 작업의 임시글을 새로 복구합니다. 카테고리 매핑을 해제한 미발행 작업에는 이전 Blogger ID를 남기지 않으며, 이미 생성된 임시글은 원래 블로그 연결을 보존합니다.
- 최신 주간 계획뿐 아니라 지난 주에서 넘어온 미완료 작업과 승인 대기 임시글도 제작 대기열에 표시합니다.
- 자동화 설정 변경, 임시글 생성·재사용, 게시글 공개 내역은 `최근 운영 기록`에 남습니다. API 키나 OAuth 토큰은 기록하지 않습니다.

## 품질·보안 게이트

- 상승 추세를 높은 신뢰도로 판정하려면 서로 다른 도메인의 확인 가능한 근거가 2개 이상 필요합니다. 카테고리와 키워드가 우선순위 점수 내림차순인지도 검증합니다.
- 설정 수량은 품질 상한입니다. 카테고리 기회점수 60점, 광고 안전성 75점, 키워드 기회점수 62점, 독창 가치·출처 확보 60점, 블로그 주제 적합도 70점 미만 후보는 자동 탈락합니다.
- 글마다 독자 상황·검색 질문·답변 약속·필수 답변·제외 범위·고유 가치가 포함된 브리프를 먼저 만듭니다.
- 글은 서로 다른 출처 2곳 이상, 1차 출처 1곳 이상, 출처에 직접 연결된 검증 주장 3개 이상이 없으면 작성하지 않습니다. 검수 점수뿐 아니라 본문에 조사 출처 링크가 실제로 포함됐는지도 코드가 확인합니다.
- Blogger에 전달되는 HTML은 허용된 제목·문단·목록·강조·인용·링크·표 태그만 남기고 스크립트, 이벤트 속성, 위험한 링크를 제거합니다.
- 운영 배포에서는 `APP_PASSWORD`, 32자 이상의 `SESSION_PASSWORD`, 32자 이상의 `APP_ENCRYPTION_KEY`가 없으면 안전하게 중단됩니다. 변경 API는 다른 출처의 브라우저 요청을 거부합니다.
- `무인 운영 준비 상태`에서 데이터베이스, 서버 API 키, Google 장기 연결, Cron 보안키, 운영 보안키, Blogger 매핑을 한 번에 확인할 수 있습니다.

처음 사용할 때 Google Cloud Console에서 **AdSense Management API**를 활성화한 뒤 앱의 `Google Blogger 연결`을 다시 눌러 읽기 전용 AdSense 권한에 동의하세요. 사령탑의 숫자 수집은 Google API가 담당하고, 전략 해석은 외부 OpenAI API를 포트폴리오 전체에 주 1회 사용합니다.

## Blogger 연결

Blogger API v3는 기존 블로그 조회와 글·페이지 관리는 지원하지만 새 블로그 생성 메서드는 제공하지 않습니다. 에이전트는 비슷한 카테고리 2~4개를 묶어 `오늘의 똑똑이`처럼 특정 주제에 종속되지 않는 이름·한 줄 소개·Blogspot 주소 후보를 추천합니다. 실제 블로그는 주제군마다 한 번만 생성하고, 에이전트에서 묶음 중 한 카테고리에 연결하면 나머지도 같은 Blogger로 자동 연결됩니다. 주소 후보의 실제 사용 가능 여부는 Blogger 생성 화면에서 확인합니다.

## Blogger 운영 대시보드

Google 계정을 연결하면 계정에서 운영 중인 Blogger를 모두 불러와 다음 항목을 보여줍니다.

- 전체 블로그 수와 게시글 수
- 최근 7일·30일·전체 누적 조회수
- 블로그별 최근 30일 조회수 비교 막대그래프
- 블로그별 게시글 수 비교 막대그래프
- 사이트별 게시글, 기간별 조회수, 게시글 수 대비 30일 조회 참고값, 최근 업데이트일
- 각 Blogger에 연결된 에이전트 카테고리
- 아직 Blogger가 연결되지 않은 카테고리와 추천 이름·소개·주소 후보

조회수는 Blogger PageViews API가 제공하는 블로그 단위 통계입니다. Blogger API는 글별 조회수를 제공하지 않으므로 글별 조회수로 표시하지 않습니다. `게시글 수 대비 30일 조회`는 블로그의 30일 전체 페이지뷰를 게시글 수로 나눈 운영 참고값이며 개별 글의 평균 조회수가 아닙니다. `통계 새로고침` 버튼을 누르면 Google에서 최신 수치를 다시 가져옵니다.

1. Google Cloud Console에서 Blogger API v3, Search Console API, AdSense Management API를 활성화합니다.
2. OAuth 동의 화면과 웹 애플리케이션 OAuth 클라이언트를 만듭니다.
3. 승인된 리디렉션 URI에 `http://localhost:3000/api/auth/google/callback`을 추가합니다.
4. `.env.example`을 `.env.local`로 복사하고 Google OAuth 값과 32자 이상의 `SESSION_PASSWORD`를 입력합니다.
5. 앱의 `Google Blogger 연결` 버튼을 누릅니다.

연결이 성공하면 상단 버튼이 `✓ Google Blogger 연결됨`으로 바뀝니다. 새
블로그를 Blogger에서 만든 뒤에는 `통계 새로고침`을 누르면 목록을 다시
조회합니다. 로그인 만료와 Blogger API 요청 오류는 서로 다른 안내로
표시되므로, API 요청 오류가 발생했다고 무조건 Google 로그인을 반복하지
않습니다. 권한 오류가 표시되면 Blogger API 활성화 여부와 블로그를 만든
Google 계정으로 로그인했는지 확인하세요.

처음 글을 만들기 전에는 대시보드 상단의 `전체 점검 실행`을 누릅니다. 이
점검은 AI 호출 없이 로컬 작업 저장소, 조사 키, 작성·검수 모델, Google OAuth
주소, 실제 Blogger 목록 요청, 카테고리 매핑을 한 번에 검사합니다. 실패
항목에는 다음 조치와 안전한 진단 단계가 함께 표시됩니다.

블로그 목록 조회는 Google 계정의 전체 Blog 리소스를 받는 최소 요청을
사용합니다. 일부 Blogger 계정에서 선택 필드나 보기 옵션을 잘못된 인자로
거부하는 경우가 있어 목록 조회 단계에는 추가 필터를 붙이지 않습니다.

수동 실행용 API 키는 최초 설정 화면에 입력할 수 있습니다. 예약 실행은 브라우저 세션을 사용할 수 없으므로 `OPENAI_API_KEY`와 선택 모델에 필요한 제공자 키를 배포 환경변수에 저장해야 합니다. OpenAI 공식 권고처럼 키를 클라이언트 코드나 공개 저장소에 넣지 마세요.

## 가장 쉬운 자동 배포 구성

1. 이 프로젝트를 Vercel에 배포합니다.
2. Vercel Marketplace의 관리형 PostgreSQL(예: Neon)을 연결해 `DATABASE_URL`을 만듭니다.
3. `.env.example`에 표시된 환경변수를 Vercel Project Settings에 등록합니다. `CRON_SECRET`, `APP_ENCRYPTION_KEY`, `SESSION_PASSWORD`는 서로 다른 32자 이상의 무작위 문자열을 사용하고, `APP_PASSWORD`에는 모바일에서 대시보드에 접속할 암호를 넣습니다.
4. Google OAuth 리디렉션 URI를 배포 주소의 `/api/auth/google/callback`으로 바꾸고 앱에서 Blogger를 다시 연결합니다. 오프라인 refresh token은 암호화되어 DB에 저장됩니다.
5. 화면에서 수량, 작성·검수 모델, 카테고리별 Blogger, 문체를 정한 뒤 `수량·자동화 설정 저장`을 누릅니다.
6. `vercel.json`의 예약이 주간 조사와 일일 작성을 호출합니다. 호스팅 요금제의 함수 최대 실행시간과 Cron 빈도 제한은 배포 전에 확인하세요.

## NEEDS_REVIEW 자동 복구

`NEEDS_REVIEW`는 하나의 재시도 버튼으로 처리하지 않습니다. 저장된 점수, 검수 문제, 코드 진단, 최종 근거 감사와 조사 문서의 출처 충돌을 함께 판독합니다.

- 검수 JSON·형식 오류: 기존 조사와 초안을 유지하고 검수만 다시 실행합니다. 같은 검수기가 형식 응답에 다시 실패하면 OpenAI 보조 검수 모델로 전환합니다.
- 사실·근거 부족: 부족하다고 지적된 주장만 표적 재검색합니다. 새 독립 출처가 확인된 문장만 수정하고, 확인되지 않은 주장은 삭제하거나 조건부 표현으로 축소한 뒤 글 전체를 재검수합니다.
- 제목·본문 품질 미달: 기존 조사자료와 통과한 내용을 유지하고 지적된 제목·도입·구성·검색 의도 항목만 수정합니다. 검수 범위는 수정 문장만이 아니라 최종 완성 글 전체입니다.
- 사람 확인: 표적 재검색 이후에도 권위 있는 출처끼리 결론이 충돌하는 경우에만 남깁니다. 자동으로 한쪽을 선택하면 사실을 왜곡할 수 있기 때문입니다.

각 카드의 `자동 판정 근거 보기`에서 원인이 된 점수와 문제 문장을 확인할 수 있습니다. 자동 실행 환경에서는 자동 복구 가능한 `NEEDS_REVIEW` 작업을 다음 실행에 이어서 처리하고, 공식 출처 충돌 작업은 임의로 공개하지 않습니다.

### 조사·작성·감수 역할 분리

- 조사는 본문 작성 전에 실행되지만 개인 블로그에 과도한 기관 수를 요구하지 않습니다. 일반 정보형 글은 ① 실제로 연 신뢰 가능한 출처 1곳 이상, ② 출처와 연결된 검증 주장 2개 이상, ③ 글의 핵심 필수 내용 2개 이상 근거 연결이라는 세 조건만 통과하면 작성을 시작합니다. 건강·금융·정책·교통·사건·연예·스포츠·실시간 정보는 같은 세 조건을 유지하되 원칙적으로 독립 출처 2곳, 검증 주장 3개, 핵심 필수 내용 3개로 한 단계 높입니다. 단, 한국장학재단·한국은행·제조사 지원문서처럼 한 공식 원문에서 핵심 항목을 모두 확인할 수 있으면 두 번째 매체를 억지로 요구하지 않습니다. 근거가 없는 부가 항목은 글 범위에서 제외하거나 확인이 필요하다고 표시합니다.
- 작성은 구조화 출력 스키마를 사용해 제목·후보·본문·메타정보를 빠짐없이 받습니다. 설명 문장 혼입과 JSON 괄호 오류를 제공자 단계에서 줄이고, 본문 길이를 제한해 긴 응답이 중간에 잘리는 위험을 낮춥니다. 작성 모델은 실제 사용한 검증 주장 ID와 필수 내용별 본문 위치를 함께 반환하며, 하나라도 누락되면 감수 단계로 넘기지 않고 작성 단계에서 자동 재시도합니다.
- 감수는 새 근거를 찾거나 내용을 억지로 채우는 단계가 아닙니다. 제목, 문장, 반복 표현, 소제목과 문단 순서, 도입부와 마지막 행동 지침을 다듬고 완성된 전체 원고를 반환합니다.
- 최종 근거 감사는 감수 뒤 원문을 독립적으로 다시 확인해 편집 과정에서 조사 범위를 벗어난 사실이 생기지 않았는지 검사합니다.

## 로컬과 배포의 차이

`DATABASE_URL`이 없으면 브라우저 저장소와 별도로 운영체제의 로컬 데이터 폴더에 계획·작업 상태·최신 검색 원본을 보관하고 수동 버튼으로 실행합니다. Windows의 기본 저장 위치는 `%LOCALAPPDATA%\BloggerWritingAgent`이며, 프로젝트 ZIP을 덮어쓰거나 폴더명을 변경해도 유지됩니다. 데이터베이스와 예약 환경변수를 갖춘 배포에서는 같은 정보를 PostgreSQL에 저장하고 화면을 열지 않아도 자동으로 실행됩니다. 실제 공개 발행만 사람 승인을 유지합니다.
